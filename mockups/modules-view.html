Status crumb — the four resting states

The crumb reads the durable, per-repo review state. State only — it never echoes the comparison (that's the inline picker's job).

Not started a diff exists, zero comments yet
In progress open threads remain
Ready all resolved · offers “Mark complete”
Archived completed · offers “Revive”

Heads-up: “Ready” is partly browser-local today — it depends on a per-browser “completed” dismissal (dismissedComplete, App.tsx:138), so it can read differently for two people on the same repo. Worth deciding whether to make it durable.

Module header anatomy

Line 1 (identity + state + stat): a neutral wayfinding band · collapse caret · repo name · status crumb · right-aligned diffstat with viewed progress (the only place the N/M count renders — the rail bar is numberless).

Line 2 (the dominant control): base [ref] … compare [ref] always inline, both ends full-width so origin/feat/checkout-redesign never truncates — followed by this module's own All / Staged / Unstaged scope (neutral active, because it repeats per module).

The header is sticky (one pins at a time) and separated from the diff by a 1px hairline — never a shadow. Only the ref-picker popover is shadowed.

What this needs in code — verified against the current source
Multi-repo scrollclient · low–moderate
No server or schema change. The per-repo GET /repos/:repo/diff already returns a self-contained RepoDiff (daemon.ts:450-471), so the client fans out N calls and stacks them. The work is lifting the single diff scalar (App.tsx:87) and the repo/worktree/target selection (App.tsx:68-70, reset effect 298-303) into per-repo collections, and re-keying session-scoped state (archiveOverrides, viewedKey, pendingSession) by repo — session ids aren't repo-qualified (Sidebar.tsx:82-85).
Remote refsserver + types + client · ~1–2h
Net-new — today only refs/heads + refs/tags are enumerated (refs.ts:21,29,67). Add refs/remotes to listRefs / searchNamedRefs (drop names ending /HEAD); add 'remote' to RefSearchKind + a remotes field (shared/index.ts:205-232); render the “Remote branches” group in groupedOptions (TargetPicker.tsx:314-325). Value is the bare origin/main.
Per-module scopeclient · folds into the above
Scope is the same per-repo target scalar as base…compare (App.tsx:70) — staged/range are mutually-exclusive kinds, part of session identity. Keeping scope in the module header (not a global toggle) means no cross-layer precedence to invent; it lifts for free with the per-repo collection.
Open questions — your call
  • Replace or mode? Should the modules view replace today's single-repo pane outright, or be an opt-in “All repos” mode alongside it? (Single-repo workspaces collapse to today's flat layout either way — rail hidden, the lone module's controls lift toward the bar.)
  • “Ready” durability. Make the completed state durable/server-side, or keep it as today's per-browser dismissal? It affects whether the crumb means the same thing for everyone on the repo.
  • Workspace bulk finish. The adversarial pass killed a top-bar “Finish all” (archive is per-repo and can partially fail). Want a secondary “Mark all ready as complete” with per-module result UI later, or strictly per-module finish?
  • Multi-remote. If a repo has more than one remote, do we sub-group the picker by remote (origin / upstream / …) or flatten them under “Remote branches”? (Deferring this; flat for v1.)
  • Module wayfinding. The bands are neutral grays right now. Want a quiet hue per module for stronger at-a-glance distinctness, or keep it structural?
